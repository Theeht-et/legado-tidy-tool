# 产品规划（据 2026-10-28 决策修订）

## 一句话

把 3000 个凌乱书源，过一遍本机流水线，得到一份「去重、验过、分好组、排好序」的 JSON。

## 四个阶段

### S1 去重（默认开，不自动删）

三层，从便宜到贵，命中即止：

1. **精确重复**：`bookSourceUrl` 归一化（协议与主机小写、去尾斜杠）+ 名称匹配键（去 emoji / 括号注释 / 营销后缀）相同。
2. **指纹重复**：21 个行为字段（搜索、发现、详情、目录、正文、`header`、`jsLib` 等）规范化后取 SHA-256，相同即同源异名。
3. **相似重复**：行为字段拼成一条长串，3-gram 集合的 Jaccard ≥ 0.92 且长度比在 0.8～1.25 之间。仅出候选，由人确认。

组内「建议保留」按规则完整度打分：行为字段填得多的、能搜索的、https 的、未禁用的优先。**永远不自动删源**，去重结果只影响导出时的 `customOrder` 与提示。

### S2 校验

用上游 Legado 引擎（不是自己写正则）对每个源跑一次搜索：

- 深度 `search`（默认）：搜索 `keyword`，取 `bookList` 规则能解出几本书。
- 深度 `search+toc`（可选）：再多跑一次目录，代价翻倍。

分类（每一类都对应一个用户动作）：

| 状态 | 含义 | 用户该做什么 |
| --- | --- |
| `ok` | 搜索出书 | 留着 |
| `no_book` | 能请求、规则能跑，但没结果 | 关键词可能太窄 |
| `timeout` | 超时（单步默认 20s） | 站点慢，可提高超时或删 |
| `network` | DNS / 连不上 / TLS | 站点已死或需代理 |
| `http_error` | 4xx / 5xx | 看状态码：403 常常是防盗链 |
| `rule_broken` | 规则跑不通（选择器全空） | 改规则或删 |
| `unsupported` | 需要浏览器渲染 / WebView | 桌面端做不到，标出来就好 |
| `no_search_url` | 没填 `searchUrl` | 这种源本来就不能搜 |
| `skipped` | 用户跳过 | — |

并发默认 200（上限 2000），单源最坏耗时 = 单步超时 × 3（搜索 1 + 目录 1 + 正文 1 已足够，不做多级重试）。
超时与并发的关系是实测过的：同一批 2386 个源，并发 200 时约 6% 超时，并发 1000 时 83% 超时——**并发拉高只会把超时变成噪声**。

### S3 整理

- 分组：源自带 `bookSourceGroup` 就保留，没有就按源类型命名（`文本` / `音频` / `图片` / `文件`）。
- 排序：组内「可用 → 超时 → 错误」，同级按中文拼音排。
- 输出：`customOrder` 写入排序值，导入阅读 App 后即按此顺序。

### S4 导出

**主路径：本地文件。** 写一个标准书源 JSON，保留所有未知字段（上游新增字段不会丢）。

**可选路径：直链。** 用户显式开启后，本机起一个只监听 `127.0.0.1` 的 HTTP 服务，把导出文件挂在一个随机路径上，在界面里给出 URL 与二维码，供同一网络/同一台机器导入。关掉开关即停。

> 二维码只在这个模式下出现。纯本地文件导出时二维码没有意义：Legado 的 QR 导入上限约 2.9KB，装不下几千个源；而本地路径也无法被手机端读取。

## 界面

Windows 单窗口，左侧四页：

1. **书源池**：导入、去重预览、勾选
2. **校验**：进度、实时日志（按状态过滤）、中止
3. **整理**：分组结果、手动改分组/排序
4. **导出**：文件名、是否清洗名称、直链开关、结果

设计约束：**能点的就别再加按钮**；所有长任务都有进度与中止；关窗口前提示未完成的任务。

## 非目标

- 手机端：校验是 CPU/网络长时间占用，不适合手机。
- 正文逐段差分：口径太细，维护成本高于收益（这是与参考项目最大的产品分歧）。
- 网盘上传 / 固定口令：引入外部依赖与合规风险。
